# 变现设计现状

日期：2026-11-06
依据：`docs/01-设计文档.md` §7（经济与解锁设计，第 210~245 行）、`:216`；`data/economy.json`（1050 B）；`docs/impl-status-2026-11-06.md`

## 结论：**无**

**没有任何变现设计。** 下面的内容都不是变现——是局内经济系统。这两件事必须分清，否则会误以为「已经有雏形」。

---

## 为什么说「无」

判断变现设计有没有，看三样东西：钱从哪进来、向谁收、收多少。逐项核：

| 项 | 状态 | 证据 |
|---|---|---|
| 内购 / 充值 | **无** | 设计文档 `:216` 明确写「不引入付费钻石类硬通货（**单机无充值场景**；若日后上小游戏平台另议）」。全仓无任何支付 SDK、无支付界面、无商品配置 |
| 广告 | **无** | 无任何广告 SDK，无激励视频，无插屏。`grep` 零命中 |
| 定价 / 售价 | **无** | 全仓无价格配置。`data/` 下 9 个 JSON（palette/heroes/enemies/waves/relics/upgrades/events/shop/economy）**没有任何一个是价格表**。`shop.json` 是**局内商店**（战斗中的能力三选一），不是商业付费商店 |
| DLC / 季票 | **无** | 无 |
| 买断制定价方案 | **无** | 设计文档未涉及售价。这是渠道侧决策，尚未做 |
| 众筹 / 赞助 | **无** | 无 |

## 容易被误认为「变现雏形」的三样东西（其实不是）

### 1. `data/economy.json` —— 这是局内经济，不是商业化

文件 1050 B / 34 行，含 `level` / `star` / `recruit` / `rarity` / `item_price` / `settle` 六块。`data_db.gd:398 _validate_economy()` 校验它。

**但它的全部作用是：玩家在游戏内用「军资」「碎片」这两种打怪得来的资源，升级武将。** 军资、碎片都**只能靠打赢得来**，**不能用真钱买**。设计文档 `:216` 写死了「单机无充值场景」。

这是**游戏内的数值循环**，属于 @秤砣 的领域，与收入无关。

### 2. 酒馆招募的「一口价」（普通 800 / 稀有 1600 / 史诗 3000 军资）

这些数字**是军资，不是人民币**。用打怪得来的军资买武将，是游戏内的资源分配决策（该攒钱买史诗，还是先升级现有队伍），不是付费点。

### 3. 「60 军资付费事件」（`docs/04-武将名册总表.md:99`）

措辞里有「付费」二字，容易误读。原文是「吕布事件付费天花板」——指的是**用 60 单位军资触发一个游戏内事件**，是局内资源消耗的设计约束。不是人民币。

**这三处措辞会在别的场合被误读成「已经有付费设计」，建议 @秤砣 在数值文档里把「付费」统一改成「军资消耗」或「资源支出」，避免歧义。**

## 如果将来要变现，现在缺什么

列出来是为了让人知道成本，不是建议现在做：

1. **定价策略** —— 买断多少钱、还是免费。这直接决定上哪个渠道（见 `platform.md`）。
2. **若做内购** —— 需要支付 SDK 接入（Steam 走 Steamworks 微交易，itch 无内购能力），需要后端校验（防篡改），需要退款政策，需要各国税务合规。**这与当前「完全离线」的架构冲突**，会引入一整套原本不存在的问题（见 `compliance.md` 里「完全离线」那条优势）。
3. **若做广告** —— 需要广告 SDK，需要联网，需要隐私政策，需要未成年人保护合规。同样破坏离线架构。
4. **若走买断** —— 最简单，只需要定价页与税务信息，架构零改动。

**我的建议（如果人问起来）：首发走 itch.io 免费试玩获取反馈，不设计任何变现；等 Steam 上架时用买断制定价。这是唯一不需要改架构的路径。**
