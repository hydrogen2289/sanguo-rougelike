| 章 | 名称 | 关数 | 首通军资 | 设计依据 |
|---|---|---:|---:|---|
| ch1 | 桃园篇 | 8 | 1190 | 既有，未动 |

| ch4 | 虎牢篇 | 8 | 2790 | 同上，董卓线 |

合计首通 **7823 军资**，绑定碎片 14 条（每条 5 枚），覆盖 11 名非初始武将。

**波次脚本的构造方式**（全部复用现有 5 种敌兵，不新增美术）：

- 每关 2~3 波，`duration 30~45`、`base_hp 20~30`、`base_atk 6~12`、`gold_total 18~30`，全部落在 `DataDB._validate_wave_entry()` 的手写剧本锚点内。
- `composition` 只用 `huangjin_zu / huangjin_gongshou / huangjin_lishi`；批次按 3 批均分，`t ∈ {0, dur×1/6, dur×1/3}`，严格 ≤ `dur×0.5` 且单调。
- `spawn_plan` 各批汇总**逐项等于** `composition`（生成时用 `divmod` 均分并由脚本 assert 校验过）。
- 敌数按章递增：ch2 单波 11~44 只，ch3 12~48，ch4 14~52；`base_atk` 上限固定在 12（锚点上限），后期压力靠**敌数与占比**而非攻击值堆，避免一击秒杀主公。
- `after` 全为空（闯关专属约束，`DataDB` 会拒）。

**已知取舍：新增三章的末关不是 Boss 关。** `01 §3.5` 与 `04 §3` 的 Boss 线（颜良&文丑 / 袁绍 / 董卓）在 `data/enemies.json` 里**没有对应单位**，`DataDB._validate_campaign()` 要求 `boss_stage=true` 时末波必须含 `ai=boss` 的敌人，而新增 Boss 需要 `scripts/battle/` 的新场景（不在我写权限内）。因此三章末关标 `boss_stage=false`，做成三波高密度攻坚关（单波 44~52 只，是本章均值的 1.3~1.5 倍）。**这是内容缺口，不是数值取舍**，见 §5。

## 3. 塔曲线：9 层起的衔接验算

**模型与校准**：初始三人组 L1 有效 DPS = 刘备 6/0.8 + 关羽 14/0.9 + 张飞 12/0.9 = **36.39**。用 `waves.json` 8 波的总有效血量 5103 与巡检实测冒烟总用时 194.5s 反推实际有效 DPS = 26.24，校准系数 **0.721**（差值是走位、目标切换、技能空转）。塔按 L = 6 + 0.7×(f−9) 的养成同步估算（即玩家爬到第 f 层时三人约在该等级）。

每层战斗时长 = `EHP × hp_growth^(f−9) / (26.2 × (1 + 0.08×(L−1)))`，占该层时长比例如下：

| 层 | 改前 (growth 1.08) 用时/层时长 | 改后 (growth 1.05) |
|---|---|---|
| F9 | 14.7s / 25s = 59% | 18.0s / 25s = **72%** |
| F12 | 21.9s / 27s = 81% | 22.1s / 27s = **81%** |
| F15 | 31.9s / 30s = 106% | 26.7s / 30s = **90%** |
| F18 | 44.1s / 32s = 138% | 30.9s / 32s = **96%** |
| F20 | 56.4s / 34s = 166% | 35.3s / 34s = **104%** |

- 改前 1.08 从 F15 起就超过层时长——玩家即使跟上养成，也清不完一波，塔在 15 层左右实质性卡死。
- 改后 1.05 把「打平」推到 F20 附近，且 9 层起占比从 72% 平滑升到 104%，**没有断崖**（相邻层最大跳幅 1.06 倍）。
- F20 之后的 104% 是刻意留的：塔内三选一、遗物、强化都不在本模型里，实际 DPS 会高于 26.2 的裸装口径。

**1~8 层到 9 层的衔接**：1~8 层直接复用 `waves.json`，W8 是华雄（1500 HP 固定值，不吃 `base_hp`）。9 层 `base_hp=30` 与 W8 的 `base_hp=30` 相同，敌数 20 只 vs W8 的「华雄 + 增援」，按 EHP 对比是 660 vs 1500——**9 层反而比 8 层轻**。这是有意的：Boss 层是机制关（杀华雄才结束 + 二阶段召唤），不该被下一层立刻数值碾压。若要让 9 层更重，只能调 `count.f0`，但那会连带把 F20 的敌数推到 36+，与同屏上限 60 冲突（`MAX_ENEMIES=60`，含 Boss 召唤），所以维持现状。

## 4. 必须先说清的一条：full 轴带宽在数学上不可达

`test_meta.gd` 的三条断言无法同时成立，**与内容量、总产出都无关**：

```
设 ce = 三人组 L1→5 消耗，cf = 三人组 L1→30 消耗，R = cf/ce，O = 管道总产出
断言1 (:372)  ce > 1600                                  # 保证 ce > 稀有将直购价
断言2 (:386)  0.8 ≤ O/(ce+1600) ≤ 1.5   =>  O ≤ 1.5·ce + 2400
断言3 (:39x)  O/cf ≥ 0.8                =>  O ≥ 0.8·R·ce

联立 2 与 3：0.8·R·ce ≤ 1.5·ce + 2400  =>  ce ≤ 2400/(0.8R − 1.5)
```

`R` 只由 `cost_exp` 决定（`cost_base` 约掉）：

| cost_exp | R = Σ(L^e, 1..29)/Σ(L^e, 1..4) | ce 上界 | 与 ce > 1600 |
|---|---:|---:|---|
| 1.0（DataDB 校验下限） | 43.5 | 72 | 矛盾 |
| 1.2 | 63.2 | 49 | 矛盾 |
| 1.4（现行） | 92.0 | 33 | 矛盾 |
| 2.5（校验上限） | 734.1 | 4 | 矛盾 |

**结论**：只要 `cost_exp ≥ 1.0`（`data_db.gd:476` 的硬下限），`ce` 上界最大也只有 72，永远低于 1600。三条断言无解，改 `cost_base`、改章节、改产出 O 都不影响这个结论。

根因是这两条轴的**分母口径差了一个数量级**：可玩窗口轴的分母是「L1→5 + 一个稀有将」，满级轴的分母是「L1→30」，而后者是前者的 92 倍（同一个 O 做分子，比值只能是 1/92 的关系）。02 §12.2-2 原意是「同一个闭环在**两个不同内容深度**下都要成立」，正确口径应当是**满级轴用「通关全部内容」的 O**，而不是复用第一章的 O。

**建议（需测试方与设计文档同步，不在我写权限内）**：把 `test_meta` 的满级轴改成
`O_all = 全部章节首通 + 全部宝箱 + 塔 1~20`（当前实测 15545），其余不变；或把满级轴从断言降级为打印项——它现在实际上已经是打印项，只有 `_pipeline_output()` 那句 `if full_ratio < 0.8: print(...)`。

即便如此，4 章口径的 full 也只有 0.0733（需 12 章才能接近 0.8）——**这是内容量问题，与数值曲线无关**，写在这里备查。
